В проекте используются абстрактные классы, наследование, свойства,
переопределение методов и полиморфизм.

## Требования

- Python 3.10 или новее.
- Сторонние библиотеки не требуются.

## Возможности

- Создание банковских счетов с уникально генерируемыми номерами.
- Пополнение и снятие средств.
- Статусы: активный, замороженный, закрытый.
- Валюты: RUB, USD, EUR, KZT, CNY.
- Проверка входных данных и обработка ошибок.
- Расчёты с использованием `Decimal`.
- Накопительные, премиальные и инвестиционные счета.

## Типы счетов

### BankAccount — обычный счёт

Реализует общие операции и проверки:

- пополнение баланса;
- снятие в пределах доступных средств;
- проверку статуса счёта;
- получение информации о счёте;
- строковое представление.

Операции пополнения и снятия разрешены только для активного счёта.

### SavingsAccount — накопительный счёт

Добавляет:

- `min_balance` — неснижаемый остаток;
- `monthly_interest_rate` — месячную ставку;
- `apply_monthly_interest()` — начисление дохода за месяц.

Начальный баланс не может быть ниже неснижаемого остатка.
Снятие ровно до этого остатка разрешено.

Доход рассчитывается по текущему балансу:

```text
Доход = баланс × месячная ставка
```

Например, при балансе 10000 и ставке 1% начисляется 100.

Ставка задаётся долей: `Decimal("0.01")` означает 1%.

Каждый вызов начисления соответствует одному условному месяцу.
Доход добавляется к балансу и учитывается при следующем начислении.
Календарь и минимальный баланс за расчётный период пока не учитываются.

### PremiumAccount — премиальный счёт

Добавляет:

- `withdrawal_limit` — лимит одного снятия без учёта комиссии;
- `overdraft_limit` — допустимую задолженность;
- `fixed_fee` — фиксированную комиссию за успешное снятие.

Настройки по умолчанию:

| Настройка | Значение |
|---|---:|
| Лимит одного снятия | 100000 |
| Лимит овердрафта | 10000 |
| Комиссия | 50 |

Комиссия списывается сверх запрошенной суммы и учитывается при проверке
овердрафта. Баланс может достигать отрицательного лимита, но не уходить ниже.

Пример:

```text
Баланс: 1000
Снятие: 1500
Комиссия: 50
Новый баланс: -550
```

Пополнение погашает задолженность.
При отклонённом снятии баланс не меняется и комиссия не списывается.

У обычного `BankAccount` отдельный числовой лимит снятия пока не задан,
поэтому сравнение лимитов между тарифами не реализовано.

### InvestmentAccount — инвестиционный счёт

Хранит отдельно:

- свободный баланс;
- виртуальный портфель с суммами вложений.

Допустимые типы активов:

- `stocks`;
- `bonds`;
- `etf`.

Метод `invest(asset_type, amount)` переводит деньги со свободного баланса
в выбранный тип активов. Он проверяет тип актива, положительность суммы
и достаточность свободных средств.

Снятие доступно только со свободного баланса.
Продажа активов не реализована.

Свойство `portfolio` возвращает копию словаря, чтобы внешнее изменение
полученных данных не меняло внутренний портфель.

Метод `project_yearly_growth(growth_rates)` рассчитывает ожидаемый
годовой прирост. Ставки передаются словарём:

```python
growth_rates = {
    "stocks": Decimal("0.10"),
    "bonds": Decimal("0.04"),
    "etf": Decimal("0.07"),
}
```

Для портфеля из 1000 в stocks, 2000 в bonds и 1000 в etf:

```text
1000 × 10% + 2000 × 4% + 1000 × 7% = 250
```

Метод возвращает прирост, а не итоговую стоимость.
Расчёт не изменяет баланс и портфель.

Ставка обязательна для каждого актива с ненулевым вложением.
Отрицательные ставки разрешены для моделирования убытка.

Все активы и ставки условные. Котировки и внешние API не используются.

## Наследование и полиморфизм

```text
AbstractAccount
└── BankAccount
    ├── SavingsAccount
    ├── PremiumAccount
    └── InvestmentAccount
```

Каждый дочерний класс переопределяет:

- `withdraw()`;
- `get_account_info()`;
- `__str__()`.

Это позволяет вызывать одинаковые методы у разных типов счетов,
получая поведение, соответствующее конкретному классу.

## Запуск

Все команды выполняются в PowerShell из корня проекта.

Создайте виртуальное окружение, если оно ещё не существует:

```powershell
py -m venv .venv
```

Запустите нужный модуль:

```powershell
.\.venv\Scripts\python.exe -B -m tests.day1
.\.venv\Scripts\python.exe -B -m tests.savings
.\.venv\Scripts\python.exe -B -m tests.premium
.\.venv\Scripts\python.exe -B -m tests.day2
```

Активация окружения для этих команд не требуется.

Флаг `-B` отключает создание новых файлов байт-кода.
Существующие папки `__pycache__` он не удаляет.

## Проверки

Файлы в `tests` содержат запускаемые демонстрации и проверки через `assert`.

- `day1.py` — базовые операции и ограничения замороженного счёта.
- `savings.py` — снятие, неснижаемый остаток, пополнение и проценты.
- `premium.py` — комиссия, овердрафт и ограничения снятия.
- `day2.py` — несколько счетов каждого типа, инвестиции, прогноз
  и полиморфизм.

Если условие `assert` нарушено, возникает `AssertionError`
с описанием ожидаемого результата.

Сообщения об ожидаемых банковских ошибках показывают, что запрещённая
операция была отклонена.

Это демонстрационные проверки, а не тесты на базе `unittest`.
Команда `unittest discover` их автоматически не выполняет.

Не запускайте проверки с флагом `-O`: он отключает инструкции `assert`.

## Исключения

| Исключение | Причина |
|---|---|
| `BankError` | Базовый класс банковских ошибок |
| `InvalidOperationError` | Некорректные данные или параметры операции |
| `InsufficientFundsError` | Недостаточно доступных средств |
| `AccountFrozenError` | Операция запрещена из-за заморозки счёта |
| `AccountClosedError` | Операция запрещена из-за закрытия счёта |

## Ограничения

- Данные хранятся в памяти и теряются после завершения программы.
- Генерация номера не гарантирует отсутствие совпадений между счетами.
- Денежные значения и ставки передаются через `Decimal`.
- Автоматическое округление денежных расчётов до копеек не реализовано.
- Отображение суммы с двумя знаками не изменяет сохранённое значение.
- Автоматическое начисление процентов по календарю отсутствует.
- Покупка реальных ценных бумаг и продажа виртуальных активов отсутствуют.
- База данных и внешние API не используются.

Проект предназначен для практики ООП и не моделирует все правила
реальной банковской системы.
