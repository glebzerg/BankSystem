## Требования

- Python 3.10 или новее.
- Для графиков нужен `matplotlib`: установка через `.\.venv\Scripts\python.exe -m pip install -r requirements.txt`.
- Текстовые отчёты и экспорт JSON/CSV используют стандартную библиотеку Python.

## Возможности

- Генерация 12-значных номеров счетов и проверка уникальности при открытии через банк.
- Пополнение и снятие средств.
- Статусы: активный, замороженный, закрытый.
- Валюты: RUB, USD, EUR, KZT, CNY.
- Проверка входных данных и обработка ошибок.
- Расчёты с использованием `Decimal`.
- Накопительные, премиальные и инвестиционные счета.
- Регистрация совершеннолетних клиентов, вход и сессии.
- Управление состоянием счетов с проверкой владельца.
- Ночные ограничения, журнал подозрительных действий, поиск и аналитика.
- Очередь транзакций, приоритеты, отложенное выполнение и отмена.
- Комиссии внешних переводов, конвертация, повторные попытки и журнал ошибок.
- Аудит в памяти и JSONL-файле, фильтрация и отчёты клиента.
- Анализ риска и блокировка опасных операций до изменения балансов.

## Типы счетов

### BankAccount — обычный счёт

Реализует общие операции и проверки:

- пополнение баланса;
- снятие в пределах доступных средств;
- проверку статуса счёта;
- получение информации о счёте;
- строковое представление.

Операции пополнения и снятия разрешены только для активного счёта.
Лимит одного снятия — 50000 в валюте счёта. Снятие ровно этой суммы
разрешено; превышение вызывает `InvalidOperationError` без изменения баланса.
Лимит доступен через свойство `withdrawal_limit` и отображается в сведениях
о счёте. Накопительный и инвестиционный счета наследуют этот лимит.

### SavingsAccount — накопительный счёт

Добавляет:

- `min_balance` — неснижаемый остаток;
- `monthly_interest_rate` — месячную ставку;
- `apply_monthly_interest()` — начисление дохода за месяц.

Начальный баланс не может быть ниже неснижаемого остатка.
Снятие ровно до этого остатка разрешено.

Доход рассчитывается по текущему балансу:

```text
Доход = баланс × месячная ставка
```

Например, при балансе 10000 и ставке 1% начисляется 100.

Ставка задаётся долей: `Decimal("0.01")` означает 1%.

Каждый вызов начисления соответствует одному условному месяцу.
Доход добавляется к балансу и учитывается при следующем начислении.
Календарь и минимальный баланс за расчётный период пока не учитываются.

### PremiumAccount — премиальный счёт

Добавляет:

- `withdrawal_limit` — лимит одного снятия без учёта комиссии;
- `overdraft_limit` — допустимую задолженность;
- `fixed_fee` — фиксированную комиссию за успешное снятие.

Настройки по умолчанию:

| Настройка | Значение |
|---|---:|
| Лимит одного снятия | 100000 |
| Лимит овердрафта | 10000 |
| Комиссия | 50 |

Комиссия списывается сверх запрошенной суммы и учитывается при проверке
овердрафта. Баланс может достигать отрицательного лимита, но не уходить ниже.

Пример:

```text
Баланс: 1000
Снятие: 1500
Комиссия: 50
Новый баланс: -550
```

Пополнение погашает задолженность.
При отклонённом снятии баланс не меняется и комиссия не списывается.

По умолчанию лимит премиального счёта вдвое выше обычного:
100000 против 50000. При создании премиального счёта можно задать
собственный положительный `withdrawal_limit`.

### InvestmentAccount — инвестиционный счёт

Хранит отдельно:

- свободный баланс;
- виртуальный портфель с суммами вложений.

Допустимые типы активов:

- `stocks`;
- `bonds`;
- `etf`.

Метод `invest(asset_type, amount)` переводит деньги со свободного баланса
в выбранный тип активов. Он проверяет тип актива, положительность суммы
и достаточность свободных средств.

Снятие доступно только со свободного баланса.
Продажа активов не реализована.

Свойство `portfolio` возвращает копию словаря, чтобы внешнее изменение
полученных данных не меняло внутренний портфель.

Метод `project_yearly_growth(growth_rates)` рассчитывает ожидаемый
годовой прирост. Ставки передаются словарём:

```python
growth_rates = {
    "stocks": Decimal("0.10"),
    "bonds": Decimal("0.04"),
    "etf": Decimal("0.07"),
}
```

Для портфеля из 1000 в stocks, 2000 в bonds и 1000 в etf:

```text
1000 × 10% + 2000 × 4% + 1000 × 7% = 250
```

Метод возвращает прирост, а не итоговую стоимость.
Расчёт не изменяет баланс и портфель.

Ставка обязательна для каждого актива с ненулевым вложением.
Отрицательные ставки разрешены для моделирования убытка.

Все активы и ставки условные. Котировки и внешние API не используются.

## Наследование и полиморфизм

```text
AbstractAccount
└── BankAccount
    ├── SavingsAccount
    ├── PremiumAccount
    └── InvestmentAccount
```

Каждый дочерний класс переопределяет:

- `withdraw()`;
- `get_account_info()`;
- `__str__()`.

Это позволяет вызывать одинаковые методы у разных типов счетов,
получая поведение, соответствующее конкретному классу.

## Система Bank — день 3

### Клиент

`Client` хранит ФИО, дату рождения, 12-значный строковый ID, контакты,
статус (`ACTIVE` или `BLOCKED`) и список номеров счетов.
При создании проверяется возраст не менее 18 лет. Для даты рождения
29 февраля в невисокосном году очередной возраст наступает 1 марта.
ID генерируется на основе UUID; повторный ID при регистрации отклоняется.
Контакты должны содержать хотя бы одну непустую пару строк.
Свойства контактов и списка счетов возвращают копии.

### Операции банка

`Bank` хранит клиентов и счета в памяти. Принадлежность счёта определяется
по ID клиента, а не по ФИО.

| Метод | Назначение |
|---|---|
| `add_client(client, password)` | Регистрация клиента |
| `authenticate_client(client_id, password)` | Проверка пароля и выдача токена |
| `open_account(session_token, account_type, ...)` | Открытие счёта |
| `freeze_account(session_token, account_id)` | Заморозка активного счёта |
| `unfreeze_account(session_token, account_id)` | Разморозка замороженного счёта |
| `close_account(session_token, account_id)` | Закрытие счёта без средств и вложений |
| `deposit(session_token, account_id, amount)` | Пополнение |
| `withdraw(session_token, account_id, amount)` | Снятие |
| `invest(session_token, account_id, asset_type, amount)` | Вложение свободных средств |
| `apply_monthly_interest(session_token, account_id)` | Начисление месячного дохода |

Типы при открытии: `standard`, `savings`, `premium`, `investment`.
Дополнительные настройки проверяются по выбранному типу.
Начальный `balance` задаёт учебные средства; реальный перевод не моделируется.
Метод возвращает сведения о счёте, а не изменяемый объект.

Закрывать можно активный или замороженный счёт с нулевым балансом
и пустым портфелем. Закрытый счёт остаётся в истории и повторно
не активируется. Попытки управлять чужим счётом отклоняются.

### Вход и безопасность

Пароли хранятся как PBKDF2-HMAC-SHA256-хеши с отдельной случайной солью.
После трёх последовательных неверных паролей клиент блокируется,
а все его сессии отзываются. Успешный вход сбрасывает счётчик ошибок.
Разблокировка клиента и срок действия сессии пока не реализованы.

С 00:00 включительно до 05:00 по московскому времени (UTC+3) запрещены
регистрация, открытие счетов, изменение их статусов и денежные операции.
Вход и чтение данных разрешены. Источник времени можно подменить:

```python
from datetime import datetime
from bank.bank import Bank

bank = Bank(
    now=lambda: datetime(2026, 11, 13, 12, tzinfo=Bank.BANK_TIMEZONE)
)
```

Журнал фиксирует блокировку входа, обращение к чужому счёту
и попытку ночной операции. События содержат время, тип, ID клиента
и описание; при ночной регистрации ID отсутствует.
Пароли и токены в журнал не записываются.
`get_suspicious_events(session_token)` возвращает копии только собственных
событий клиента. После блокировки доступ через сессии прекращается.

### Поиск и аналитика

`search_accounts(session_token, ...)` ищет только собственные счета.
Необязательные фильтры: точный `account_id`, `account_type`, `status`, `currency`.
Несколько фильтров применяются одновременно; без совпадений возвращается
пустой список. Закрытые счета также доступны для поиска.

`get_total_balance()` возвращает суммы отдельно по валютам.
`get_clients_ranking(currency)` сортирует клиентов по убыванию средств
в выбранной валюте; при равенстве — по ID.
Учитываются портфель и задолженность. Замороженные счета и средства
заблокированных клиентов включаются, закрытые счета пропускаются.
Клиенты без средств в выбранной валюте получают нулевую сумму.

Аналитические методы являются сводками уровня банка и не проверяют
клиентскую сессию. Роли сотрудников и разграничение доступа к аналитике
в пользовательском интерфейсе пока не реализованы.

## Транзакции — день 4

`Transaction` хранит поручение: UUID, тип, сумму, валюту, участников,
рассчитанную комиссию, статус, причину отказа, времена и число попыток.
Поддерживаются пополнение, снятие, внутренний и моделируемый внешний перевод.

Обязанности разделены между тремя классами:

- `Transaction` проверяет данные поручения и допустимость переходов статуса.
- `TransactionQueue` хранит ожидающие операции. Больший приоритет выполняется
  раньше; при равном приоритете действует порядок добавления. Будущая операция
  не блокирует готовые. Получение операции переводит её в `PROCESSING`.
- `TransactionProcessor` рассчитывает условия, выполняет операцию и сохраняет
  результат. Временный сбой до списания допускает повтор через 60 секунд,
  максимум 3 попытки всего. Повтор получает обычный приоритет 0.

Обычный путь: `CREATED → QUEUED → PROCESSING → COMPLETED`.
Окончательный отказ — `FAILED`, отмена ожидающей операции — `CANCELLED`.
При временной ошибке процессор проходит через `RETRY_PENDING` и возвращает
операцию в `QUEUED` с будущим временем. Журнал сохраняет каждую ошибку отдельно.

Внешняя комиссия — 1% сверх суммы, в валюте отправителя. Внутренние переводы
бесплатны. Комиссия премиального счёта за снятие применяется только к снятию.
Перевод учитывает минимальный остаток накопительного счёта и овердрафт
премиального; лимит снятия наличных к переводам не применяется.

Сумма перевода задаётся в валюте отправителя, пополнения — получателя.
Для конвертации между нашими счетами в `Bank(exchange_rates=...)` передаются
направленные пары, например `{(Currency.RUB, Currency.USD): Decimal("0.01")}`.
Обратный курс автоматически не вычисляется. Комиссия внешнего перевода и
сумма конвертации округляются до двух знаков через `ROUND_HALF_UP`.
Поручения с долями копейки процессор отклоняет.

Клиентские методы банка:

- `create_transaction(...)` проверяет сессию и владельца, ставит поручение
  в очередь и возвращает снимок данных в словаре.
- `get_transaction(...)` и `get_transactions(...)` показывают только поручения
  текущего клиента. Получатель не получает доступ к поручению отправителя.
- `cancel_transaction(...)` отменяет собственное ожидающее поручение.
- `get_transaction_errors(...)` возвращает копии записей своего журнала.

`process_transactions()` — служебный запуск управляющего кода банка без
клиентской сессии, возвращающий число обработанных попыток. С 00:00 до 05:00
по Москве запуск запрещён, очередь остаётся нетронутой. Перед каждой попыткой
повторно проверяются владелец и блокировка участников; счета проверяют
заморозку, закрытие и доступные средства. Время планирования требует часовой пояс.

Демонстрация `tests.day4` создаёт ровно 10 поручений. Для этого пакетного сценария
задан `RiskAnalyzer(frequency_limit=10)`; обычный банк использует порог 5 операций
за минуту. Сначала выполняются готовые операции, затем учебные часы переводятся на минуту для повтора и
ещё на минуту для отложенного перевода. Реального ожидания нет.
Итог: 7 успешных операций, 2 отказа, 1 отмена. Балансы: отправитель 7194 RUB,
премиальный счёт −1400 RUB, получатели 2700 RUB и 10 USD.
Нулевой начальный баланс отправителя подтверждает работу приоритета:
пополнение добавлено восьмым, но выполняется раньше переводов.

## Аудит и риск-анализ — день 5

`AuditLog` хранит неизменяемые записи с уровнями `INFO`, `WARNING`, `ERROR`,
`CRITICAL`. Записываются отказы входа, блокировки, подозрительные действия,
оценки риска, успехи, ошибки, повторы и отмены денежных операций.
Пароли и токены сессий банк в записи не передаёт.

Чтобы включить файл, передайте журнал банку:

```python
from bank.audit import AuditLevel, AuditLog
from bank.bank import Bank

audit = AuditLog(file_path="audit.jsonl")
bank = Bank(audit_log=audit)
warnings = audit.filter(level=AuditLevel.WARNING)
```

Без `file_path` журнал работает только в памяти. Файл сохраняется в UTF-8:
одна запись на строку JSONL. Существующие записи не перезаписываются.
Родительская папка должна существовать. Новый объект журнала дописывает файл,
но не загружает старые записи в память. Фильтры по `level`, `client_id`,
`transaction_id`, `start_at`, `end_at` применяются вместе и возвращают кортеж.
Даты требуют часовой пояс, обе границы периода включены.

`RiskAnalyzer` использует учебные правила:

| Признак | Условие по умолчанию | Баллы |
|---|---|---:|
| Крупная сумма | От 100000 RUB, 1000 USD/EUR, 500000 KZT или 10000 CNY | 2 |
| Частые операции | От 5 разных операций клиента за минуту, включая текущую | 2 |
| Новый получатель | Клиент ещё не совершал успешный перевод этому счёту | 1 |
| Ночное время | С 00:00 включительно до 05:00 исключительно по Москве | 1 |

Низкий риск — 0 баллов, средний — 1–2, высокий — от 3.
Пороги сумм, частоты, ночной интервал и границы уровней настраиваются
в конструкторе `RiskAnalyzer`; анализатор передаётся как `Bank(risk_analyzer=...)`.
Валюты сравниваются со своими порогами без конвертации.
У внешнего получателя учитываются номер счёта и ID банка вместе.

Высокий риск вызывает `HighRiskTransactionError`. В очереди поручение получает
`failed` без автоматического повтора; прямой метод банка передаёт исключение
вызывающему коду. Деньги и комиссии не списываются. Низкий и средний риск
позволяют продолжить обычные проверки операции. Клиент при этом не блокируется.

Проверка выполняется перед каждой попыткой, включая отложенные операции
и повторы. Прямые `deposit()`, `withdraw()`, `invest()` и очередь используют
общую историю частоты. Повтор одной транзакции учитывается один раз;
получатель становится знакомым только после успеха. Начисление процентов
фиксируется в аудите, но не увеличивает частоту клиентских операций.
Ночной запрет банка сохраняется и срабатывает до оценки риска: очередь остаётся
нетронутой, а ночная попытка записывается как событие безопасности.

Отчёты доступны только по действующей сессии своего клиента:

```python
suspicious = bank.get_suspicious_operations(token)
profile = bank.get_client_risk_profile(token)
errors = bank.get_error_statistics(token)
```

Все три метода принимают `start_at` и `end_at`. Подозрительные операции —
среднего и высокого риска, одна строка на операцию с максимальной оценкой
и последним результатом за период. Профиль содержит распределение уровней,
число блокировок и частоту причин выбранных максимальных оценок.
Неоценённые операции в профиль не включаются. Более поздние результаты
не появляются в отчёте за прошлый период.

Статистика ошибок денежных операций разделяет `failed_attempts`,
`failed_operations`, `risk_blocked_operations` и группировку `by_error_type`.
Временный сбой с последующим успехом увеличивает только число неудачных попыток.
Ошибки входа и незаписанные события в эту статистику не входят.

Демонстрация `tests.day5` создаёт 8 поручений: 5 успешных, 2 отказа и 1 отмена.
Также выполняется прямое пополнение и отклоняется ночное снятие.
Профиль содержит 8 оценённых операций: 4 низкого, 3 среднего и 1 высокого риска.
Статистика показывает 4 неудачные попытки, 3 окончательных отказа и 1 блокировку
по риску. Итоговые балансы: отправитель 99800 RUB, знакомый получатель 100200 RUB,
новый получатель 0 RUB. Время управляемое, реального ожидания нет.
Журнал `audit_day5.jsonl` остаётся в корне проекта и дописывается при повторном
запуске. Отчёты демонстрации используют только события текущего запуска.

## Демонстрационная программа — день 6

Вся демонстрация находится в `tests/day6.py` и использует готовые методы банка.
Создаются 5 клиентов и 10 счетов четырёх типов, все суммы в RUB.
Данные фиксированы, время управляемое, случайных сценариев и реального ожидания нет.

Сначала выполняются 20 обычных транзакций: пополнения, снятия и внутренние переводы.
Через две учебные минуты выполняются ещё 10, включая внешний перевод с комиссией,
недостаток средств, замороженный счёт, превышение лимита и две блокировки по риску.
В консоли видны постановка каждого поручения в очередь, результат и причина отказа.

Итог — 30 транзакций: 25 выполнено, 5 отклонено. Для Ивана выводятся счета,
история и подозрительные операции. Затем показываются статистика транзакций,
топ-3 клиентов и общий баланс **293749.50 RUB**.
Топ-3: Иван — 206200 RUB, Павел — 27900 RUB, Мария — 23900 RUB.
Через `assert` проверяются количество клиентов, счетов и транзакций, балансы
всех счетов, причины отказов, комиссия, порядок топ-3 и отсутствие оставшихся
поручений в очереди.

## Отчётность и визуализация — день 7

`ReportBuilder` собирает независимые снимки трёх типов: по клиенту, по банку
и по рискам клиента. Форматирование, экспорт и графики используют один снимок,
не выполняют поручения и не читают банк повторно.

```python
from bank.report_builder import ReportBuilder

builder = ReportBuilder(bank)
client_report = builder.build_client_report(token)
bank_report = builder.build_bank_report()
risk_report = builder.build_risk_report(token, start_at=start, end_at=end)

print(builder.to_text(client_report))
builder.export_to_json(client_report, "reports/client/report.json")
builder.export_to_csv(client_report, "reports/client/csv")
builder.save_charts(client_report, "reports/client/charts")
```

Клиентские отчёты требуют действующую сессию и содержат только свои данные.
`build_bank_report()` — служебный метод управляющего кода, как общий баланс банка.
Пароли и токены в снимки не включаются. Период поддерживается в риск-отчёте;
обе границы включены, даты должны содержать часовой пояс.

В финансовых отчётах отдельно показаны свободные деньги и суммы с портфелем,
каждая валюта считается отдельно. Закрытые счета остаются в списке и истории,
но не включаются в денежные итоги. Статистика транзакций и комиссии относятся
к поручениям очереди; комиссия учитывается только после успешного исполнения,
даже если потребовалось несколько попыток. Прямые пополнения, снятия и инвестиции
видны в истории баланса и отчётах по риску, но не увеличивают количество поручений
очереди. Начисление процентов входит в баланс и его историю без оценки риска.

Форматы экспорта:

- Текст — русские подписи, таблицы, суммы с двумя знаками и пояснения пустых разделов.
- JSON — весь снимок в UTF-8; деньги сохраняются строками без потери точности,
  даты — в ISO 8601 с часовым поясом.
- CSV — отдельная таблица на раздел, UTF-8 с BOM, разделитель `;`.
  Сводка сохраняется строками `metric/value`, портфели и причины риска — отдельными
  таблицами. Пустые таблицы сохраняют заголовки, `None` становится пустой ячейкой.
  При чтении CSV программой укажите `encoding="utf-8-sig"` и `delimiter=";"`.
- PNG — диаграммы с помощью `matplotlib`, без открытия окон.

Есть круговая диаграмма статусов поручений, столбчатые диаграммы свободных
балансов счетов клиента, средств клиентов банка с портфелями и уровней риска.
Валюты не смешиваются на одной денежной диаграмме. Для пустых данных выводится
пояснение, отрицательный баланс показывается ниже нуля.

История баланса сохраняется при открытии счёта и после успешных операций через
`Bank`. Комиссии, проценты, конвертация и инвестиции учитываются по фактическому
остатку. Отказы, отмены и неудачные повторы не добавляют точек.
`bank.get_balance_history(token, account_id)` возвращает неизменяемый снимок
истории своего счёта. История отражает свободные деньги, без стоимости портфеля.

В клиентский набор графиков входят ступенчатые линии баланса по каждому счёту.
`save_charts(report, directory, account_id=account_id, dpi=150)` ограничивает
только линии выбранным счётом; остальные диаграммы остаются по всему снимку.
Выбор счёта доступен только для клиентского отчёта. Метод возвращает список
путей PNG и освобождает фигуры даже при ошибке. `build_charts(report)` возвращает
сами фигуры для дальнейшей работы; после использования вызывайте `figure.clear()`.

Папки экспорта создаются автоматически. Повторный экспорт заменяет файлы;
JSON, каждый CSV и каждый PNG заменяются отдельно через временный файл.
Для разных отчётов используйте разные папки. Ошибка записи вызывает
`ReportExportError`; некорректные данные — `InvalidOperationError`.

Демонстрация `tests.day7` создаёт 3 клиентов, 6 счетов и 5 поручений:
2 успешных и 3 отказа. Также показывает прямое пополнение, инвестицию и проценты.
Итоги банка: **18909 RUB и 200 USD**, комиссия успешных поручений — **1 RUB**.
Для Ивана свободные деньги — **11899 RUB**, с портфелем — **12399 RUB**;
риск-профиль: 2 операции низкого, 3 среднего и 1 высокого риска.

Каждый запуск создаёт отдельную папку `reports/day7/<время_запуска>/` с разделами
`client`, `bank`, `risk`. В них сохраняются 3 TXT, 3 JSON, 20 CSV и 8 PNG суммарно.
Сценарий проверяет суммы между форматами и чтение PNG, использует учебные часы
без реального ожидания. Созданные файлы исключены из Git.

## Запуск

Все команды выполняются в PowerShell из корня проекта.

Создайте виртуальное окружение, если оно ещё не существует:

```powershell
py -m venv .venv
```

Установите зависимость для графиков Day7 и полного набора тестов:

```powershell
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
```

Запустите нужный модуль:

```powershell
.\.venv\Scripts\python.exe -B -m tests.day1
.\.venv\Scripts\python.exe -B -m tests.savings
.\.venv\Scripts\python.exe -B -m tests.premium
.\.venv\Scripts\python.exe -B -m tests.day2
.\.venv\Scripts\python.exe -B -m tests.day3
.\.venv\Scripts\python.exe -X utf8 -B -m tests.day4
.\.venv\Scripts\python.exe -X utf8 -B -m tests.day5
.\.venv\Scripts\python.exe -X utf8 -B -m tests.day6
.\.venv\Scripts\python.exe -X utf8 -B -m tests.day7
```

Активация окружения для этих команд не требуется.

Флаг `-B` отключает создание новых файлов байт-кода.
Существующие папки `__pycache__` он не удаляет.
Флаг `-X utf8` позволяет выводить Unicode-символы демонстраций в Windows.

## Проверки

В `tests` находятся демонстрации с `assert` и автоматические тесты `unittest`.

- `day1.py` — базовые операции и ограничения замороженного счёта.
- `savings.py` — снятие, неснижаемый остаток, пополнение и проценты.
- `premium.py` — комиссия, овердрафт, ограничения снятия и сравнение
  обычного лимита с повышенным премиальным.
- `day2.py` — несколько счетов каждого типа, инвестиции, прогноз
  и полиморфизм.
- `day3.py` — регистрация, счета, доступ, ночной запрет, журнал и аналитика.
- `day4.py` — 10 транзакций, приоритет, задержка, отмена, комиссия, обмен,
  овердрафт, отказы и успешный повтор; итоговые балансы проверяются через `assert`.
- `day5.py` — четыре признака риска, блокировка, повтор, JSONL и три отчёта;
  результаты и балансы проверяются через `assert`.
- `day6.py` — комплексная симуляция: 5 клиентов, 10 счетов, 30 транзакций,
  ошибки, подозрительные операции, пользовательский сценарий и итоговые отчёты.
- `day7.py` — три типа отчётов, TXT/JSON/CSV/PNG, сверка денежных итогов
  между форматами и проверка сохранённых изображений.

В демонстрации дня 3 используется управляемое время: результат не зависит
от настоящего часа запуска. Итог — 7370 RUB: Анна 4450, Иван 2920.

Если условие `assert` нарушено, возникает `AssertionError`
с описанием ожидаемого результата.

Сообщения об ожидаемых банковских ошибках показывают, что запрещённая
операция была отклонена.

Для запуска всех автоматических тестов:

```powershell
.\.venv\Scripts\python.exe -B -m unittest discover -s tests -t . -p "*.py" -v
```

Шаблон `*.py` нужен, поскольку файлы автоматических тестов не имеют
стандартного префикса `test_`. Команда запускает классы `unittest`,
но не вызывает `main()` демонстраций — их запускают отдельно.

Не запускайте проверки с флагом `-O`: он отключает инструкции `assert`.

## Исключения

| Исключение | Причина |
|---|---|
| `BankError` | Базовый класс банковских ошибок |
| `InvalidOperationError` | Некорректные данные или параметры операции |
| `InsufficientFundsError` | Недостаточно доступных средств |
| `TemporaryTransactionError` | Временный сбой до списания, допускающий повтор |
| `HighRiskTransactionError` | Высокий риск: отказ до списания без автоматического повтора |
| `AuditWriteError` | Не удалось записать событие аудита в файл |
| `ReportExportError` | Не удалось сохранить JSON, CSV или PNG отчёта |
| `AccountFrozenError` | Операция запрещена из-за заморозки счёта |
| `AccountClosedError` | Операция запрещена из-за закрытия счёта |
| `AuthenticationError` | Неверные учётные данные или недействительная сессия |
| `ClientBlockedError` | Доступ клиента заблокирован; наследник `AuthenticationError` |

## Ограничения

- Клиенты, счета, очередь и история риска хранятся в памяти и теряются после
  завершения программы. Аудит можно дописывать в файл; загрузка из файла не реализована.
- История балансов также хранится в памяти и учитывает операции только через
  `Bank`. Экспортированные отчёты не являются резервной копией банка;
  восстановление объектов из JSON/CSV не реализовано.
- Уникальность номеров проверяется внутри `Bank`; отдельные объекты счетов
  вне банка могут получить совпадающие номера.
- Проверки сессий, владельца и времени действуют при операциях через `Bank`.
  Прямой вызов методов объекта счёта не выполняет проверки банка, включая риск.
- Аудит рассчитан на одного писателя. Сбой записи до выполнения останавливает
  денежную операцию. Если ошибка аудита возникла после успеха или отмены,
  результат сохраняется, а вызывающий код получает `AuditWriteError`.
  Автоматического отката файловых записей и уже выполненных операций нет.
- Денежные значения и ставки передаются через `Decimal`.
- Округление до копеек применяется к конвертации и внешней комиссии;
  прямые операции счетов и начисление процентов сохраняют прежнюю точность.
- Отображение суммы с двумя знаками не изменяет сохранённое значение.
- Автоматическое начисление процентов по календарю отсутствует.
- Покупка реальных ценных бумаг и продажа виртуальных активов отсутствуют.
- База данных и внешние API не используются.
- Очередь рассчитана на один поток и не восстанавливается после перезапуска.
- Внешний перевод моделируется списанием; реального зачисления в другой банк нет.
- `external_preflight` моделирует проверку доступности внешнего банка до
  списания. Эта функция не должна отправлять перевод или изменять балансы.

Проект предназначен для практики ООП и не моделирует все правила
реальной банковской системы.
